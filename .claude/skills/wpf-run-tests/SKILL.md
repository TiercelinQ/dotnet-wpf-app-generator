# /wpf-run-tests — Executable verification

## Role
QA engineer — prove the project is clean and buildable with real commands.

## Goal
Run the verification ladder, surface any failure with its output, and confirm a clean state or hand off failures to `/wpf-fix-issue`.

## Deliverable
A short report in the user's language stating what passed, with command output as proof; or a list of failures.

---

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Steps

1. **Apply `@rules/verification.md §A`** in order:
   ```
   dotnet restore                              # packages resolve (Central Package Management)
   dotnet build -c Debug                       # expect clean — warnings are errors
   dotnet format --verify-no-changes           # format + analyzers — expect no pending change
   dotnet test                                 # only if tests were enabled in Phase 1
   dotnet publish src/App.Wpf -c Release -p:PublishProfile=win-x64   # only when packaging is requested - project path mandatory, app closed
   ```
   - `NU1008` on build → a `Version` on a `PackageReference`; move it to `Directory.Packages.props`.
   - `dotnet format` reporting changes → run it once without `--verify-no-changes` to apply, then re-check; never mix a formatting-only diff into a feature change.
   - If the Salesforce CLI integration is on, the static read-through (`@rules/verification.md §B`) confirms every `sf` call goes through `Services/SfCliService.cs` with `UseShellExecute = false` and an `ArgumentList`, started from a service. Tests never start the real `sf` — the service is substituted (`@rules/tests.md`).
2. **Capture output**. A non-zero exit or any reported error is a failure — quote the relevant lines.
3. **Report** (in the user's language): which commands passed, with proof. On failure: name the command, the `file(line,col)` and the rule id, and hand off to `/wpf-fix-issue` for the root cause (do not patch here unless the user asks).
4. If the **.NET SDK is not available**: say so plainly, do the static read-through (`@rules/verification.md §B`), and list the exact commands the user must run themselves. Never claim a clean build you could not execute.

## Test creation policy

- Tests are opt-in at Phase 1. If enabled, the suite (xUnit v3) was delivered in its dedicated batch — run it (`dotnet test`).
- **Do not create a test project if the project has none** (Phase 1 tests = No). The default verification is restore + build + format.
- If the user **explicitly asks** to add tests later: follow `@rules/tests.md` (xUnit v3 + NSubstitute, layer coverage, substituted services, in-memory SQLite). Confirm scope, then add the test project, its reference to the app project, and the test packages in `Directory.Packages.props`.

## Anti-patterns — what NOT to do
- **Do not** report "all green" without having actually run the commands (or without flagging that the env was unavailable).
- **Do not** fix code silently inside this skill — verification reports; fixing is `/wpf-fix-issue` (root cause) or `/wpf-add-feature`.
- **Do not** scaffold tests or add a test runner the user did not ask for.
- **Do not** lower a check (disable an analyzer, drop `TreatWarningsAsErrors`, skip the format check) to make the report pass.

## When the user asks something adjacent
- **"Make the build pass"** → if it fails, the root cause is in code/config; classify with `/wpf-fix-issue`. Do not disable checks to force green.
- **"Add coverage"** → that is explicit test creation; confirm scope + runner, then write tests.
