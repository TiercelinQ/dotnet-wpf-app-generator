# /wpf-trace-feature — Analyze a generated WPF app

## Role
Analyst — trace and explain how something works, without changing it.

## Goal
Give the user an accurate, layered understanding of a feature or behavior, with exact code references.

## Deliverable
A structured report (in the user's language) with `file:line` references. Optionally `docs/specs/analyse-[topic].md` if the user wants it persisted.

---

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Steps

1. **Identify scope** — a single file, an entity (model+service+viewmodel+view), a cross-cutting pattern (theming, error handling, threading, DI, security), or the whole app.

2. **Ask when ambiguous** — if the request has several valid readings, use `AskUserQuestion` before diving in. See "When to ask" below.

3. **Read the relevant sources** by layer:
   - Contract & specs: `docs/specs/04-architect.md` (structure of truth), other `docs/specs/*`.
   - Composition root: `App.xaml`, `App.xaml.cs` (DI registrations, global handlers, theme, splash).
   - Constants: `AppConfig.cs`.
   - Models: `Models/[Entity].cs`, `Models/Errors.cs`, `Models/Result.cs`.
   - Services: `Services/[Entity]Service.cs`, `Services/Data/`, `Services/PreferencesService.cs`, `Services/SfCliService.cs` (if the Salesforce integration is on: runner + typed helpers; `sf-cli-reference/INDEX.md` is the command/flag reference, consulted on demand).
   - ViewModels: `ViewModels/ShellViewModel.cs`, `ViewModels/[Entity]ViewModel.cs`.
   - Views: `Views/MainWindow.xaml`, `Views/[Entity]View.xaml`, `Views/Layout/`.
   - Themes: `Themes/Tokens.xaml`, `Themes/Tokens.*.xaml`, `Themes/Styles.xaml`.
   - Binding refs (read on demand, not auto-imported): `design-system.md`, `layout.md` — for design-system/layout deviations.

4. **Trace the flow** following the unidirectional path: view (binding / command) → ViewModel (`[RelayCommand]`) → service interface → service implementation (data or process) → model. For an `sf` feature: `OrgView` → `OrgViewModel` command → `ISfCliService` → `Process` with an `ArgumentList` → `sf --json` → parsed envelope → `Result`. For errors: service converts an exception → `Result<T>` → ViewModel → snackbar. For theming: token key → `Themes/Tokens.xaml` → `{DynamicResource}` in `Themes/Styles.xaml`. Cross-reference every service against its DI registration in the composition root.

5. **Report** (in the user's language):
   - What the code does (behavior).
   - How it connects across layers (dependencies, data flow, commands, DI lifetimes).
   - Any inconsistency vs the contract or the rules (`rules/*`), with the rule named — including security (`@rules/security.md`) and threading (`@rules/threading.md`).
   - `file:line` references.
   - **Flag any unverified assumption explicitly** — do not fabricate a runtime behavior you could not read.

## When to ask the user

Use `AskUserQuestion` when:
- **Multiple valid scopes** — "analyze the settings page" could mean the view, the ViewModel, the preferences service, or all.
- **Multiple readings** — "how does saving work" — which entity? the command? the SQLite write? the validation?
- **Depth vs breadth** — a deep audit of one entity vs a survey of several.
- **Output format** — short summary, structured report, or actionable findings list.

Offer 2–4 concrete options, recommended one first. Do not ask when the scope is obvious or you are just confirming a fact.

## Anti-patterns — what NOT to do
- **Do not** modify code during an analysis. This skill is read-only; if a fix is wanted, hand off to `/wpf-fix-issue` or `/wpf-add-feature`.
- **Do not** report a behavior you inferred but did not read — mark it as an assumption and offer to verify.
- **Do not** describe the layers in the abstract — anchor every claim to a `file:line`.
- **Do not** silently pick one interpretation when several exist — ask.

## When the user asks something adjacent
- **"And fix it"** → switch to `/wpf-fix-issue` (bug) or `/wpf-add-feature` (change), carrying the analysis findings.
- **"Is this secure / well-architected?"** → compare against `@rules/security.md`, `@rules/threading.md`, `docs/specs/04-architect.md`, and `@rules/mvvm.md`; report deviations, do not refactor (that is `/wpf-refactor-code`, on request).
