# /wpf-fix-issue — Fix a bug (root cause)

## Role
Debugger — find the root cause and fix it cleanly, never paper over it.

## Goal
Resolve the failure so the relevant `@rules/verification.md` checks pass, with the minimum correct change.

## Deliverable
The corrected file(s) on disk + a passing verification + (after a multi-attempt anomaly) a cleanup report.

---

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Decision tree — classify the failure first

Read the actual error before touching code. Classify, then act in this order:

### 1. Build / analyzer error (`dotnet build`, `dotnet format`)
- Read the exact message + `file(line,col)` + the rule id (`CSxxxx`, `CAxxxx`, `IDExxxx`). Most are precise (type mismatch, nullable warning, unused symbol, missing using).
- Fix the cause. **Do not** add `#pragma warning disable` or a `!` null-forgiving operator to silence it unless the analyzer is genuinely wrong and the reason is written in a comment on the line above.
- `NU1008` → a `Version` was written on a `PackageReference` while Central Package Management is on; move it to `Directory.Packages.props` (`@rules/config.md`).
- XAML parse error at build (`MC3000`, `MC3074`) → an unknown element or a missing namespace declaration; check the `xmlns` prefixes and the resource dictionary merge order (`@rules/xaml.md`).

### 2. Startup failure
- The window never appears → an exception in `App.xaml.cs` before `Show()`. Check the host build, the DI registrations (a missing registration throws on resolve), and the migration run (`@rules/db.md`).
- `StartupUri` set **and** a manual `Show()` → two windows or an unexpected shutdown. `App.xaml` carries no `StartupUri` (`@rules/splash.md`).
- The app exits right after the splash → `ShutdownMode` closing the app with the splash. The shell is the main window.

### 3. Runtime exception
- **UI thread**: caught by `DispatcherUnhandledException`? Identify the ViewModel or the view. Binding failure, null state, or an unguarded conversion.
- **Background**: caught by `AppDomain.UnhandledException` or surfaced as an unobserved task? Almost always an `async void` or a fire-and-forget task (`@rules/threading.md`).
- `InvalidOperationException: The calling thread cannot access this object` → a cross-thread touch of a bound object. Fix by marshalling or, better, by restructuring so the value is assigned on the UI thread (`@rules/threading.md`). Never "fix" it by wrapping everything in `Dispatcher.Invoke`.
- Fix at the layer that owns the cause, not where the symptom surfaces.

### 4. Binding failure (the UI shows nothing / a stale value)
- Trace it **end-to-end**: the ViewModel property (is it `[ObservableProperty]`, does it raise the change notification?) ↔ the `DataContext` (resolved by the container?) ↔ the binding path and mode ↔ the converter.
- Turn on the binding trace (`PresentationTraceSources.TraceLevel=High` on the binding) and read the output window — a silent binding failure is logged there, not thrown.
- A collection that does not refresh is usually a `List<T>` where an `ObservableCollection<T>` is required, or a mutation off the UI thread.

### 4b. Salesforce CLI failure (if the integration is on)
- Process start fails with "file not found" → `sf` not installed or not on `PATH`; point to the install + the `SfPath` preference. On Windows, confirm the runner handles the `sf.cmd` shim (a bare `Process.Start` with `UseShellExecute = false` cannot execute a `.cmd`).
- The call hangs → one output stream read to the end before `WaitForExit`; both reads must start before the wait (`@rules/sf-cli.md`).
- Non-JSON / unreadable output → CLI version drift or a command run without `--json`; verify the flags against the matching `sf-cli-reference/` section (`sf <cmd> --help`).
- `status != 0` in the envelope → read `message`/`name`, return it as a `Result` failure; never throw out to the ViewModel. See @rules/sf-cli.md.

### 5. Security gap (`@rules/security.md`)
- Data written beside the executable, a secret in code or in `preferences.json`, an unvalidated input, an unconfined path, a concatenated SQL string, a process started with `UseShellExecute = true`. These are never "acceptable for now" — fix to the rule.

### 6. Theming deviation (visual bug)
- Hardcoded color/size/margin, a themed brush referenced with `StaticResource`, a dictionary merged in the wrong order, a `DropShadowEffect`, a `MessageBox` for a business error. Route the value through `Themes/Tokens.xaml` / `Themes/Styles.xaml`, or replace the native dialog with the styled dialog/snackbar. See `@rules/xaml.md` / `@rules/errors.md`.

## Steps

Read `design-system.md` / `layout.md` on demand if the fix touches UI (no longer auto-imported).

> **Legacy theming**: if the app predates the Fluent baseline (README reference — see `/wpf-load-project` step 5), fix within the app's own conventions; do not introduce the current baseline's visuals into a legacy app. The upgrade path is `/wpf-migrate-design`, on request.

1. Get the real error (command output, stack trace, binding trace, or the user's repro). If you cannot reproduce, ask for the exact message — do not guess.
2. Classify with the tree above; read both the failing site and the declaration it depends on.
3. **Ask: "knowing what I know now, what is the clean fix?"** Implement that, not the quickest patch. If the clean fix is larger than expected, say so before applying.
4. Apply the minimum correct change. Respect the layers, the contract (`docs/specs/04-architect.md`), and the security and threading rules.
5. **Verify**: re-run `@rules/verification.md §A` for the affected area; confirm the targeted failure is gone and nothing else broke. Then apply `@rules/readme.md` — if the fix changed a README-documented aspect (DB schema/migration, package, structure), regenerate the README.
6. **Changelog**: append a `### Fixed` entry under `## [Unreleased]` in `docs/release/CHANGELOG.md` (`@rules/versioning.md`) — in English, one concise line, no version bump (the bump happens at `/wpf-release`). If the file is absent (legacy app), skip silently and suggest `/wpf-load-project` to initialize it. Skip for a non-code fix with no user-visible effect (e.g. a doc typo).
7. If it took several attempts: produce the **cleanup report** (`@rules/mvvm.md` — list every dead element added during failed attempts), then offer `Do you want to remember this point? /wpf-save-memory`.

## Anti-patterns — what NOT to do
- **Do not** silence a compiler or analyzer finding with `#pragma warning disable` or `!` instead of fixing the cause.
- **Do not** weaken a security rule to make an error disappear — fix the actual cause within `@rules/security.md`.
- **Do not** wrap a bug in an empty `catch` that hides it.
- **Do not** blanket-wrap code in `Dispatcher.Invoke` to make a cross-thread exception go away — find what runs off the UI thread and why.
- **Do not** hardcode a value to "make it look right" — fix it through the resource keys.
- **Do not** patch one link of a broken binding chain and leave the rest inconsistent.
- **Do not** leave failed-attempt residue in the file. Clean it up.
- **Do not** expand the fix into an unrequested refactor; flag genuinely-wrong surrounding code for `/wpf-refactor-code`.
- **Do not** claim it is fixed without re-running the verification (or telling the user which command to run if no env).

## When the user asks something adjacent
- **"Just make the error go away"** → the error is a symptom; explain you are fixing the cause. A genuine temporary silence is explicit and flagged as debt.
- **"It's slow / janky"** → not a crash; optimization (virtualization on long lists, binding churn, work on the UI thread) — handle as a finalization or `/wpf-refactor-code` item, on request.
