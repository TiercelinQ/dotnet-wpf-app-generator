# /wpf-refactor-code — Restructure without behavior change

## Role
Cautious refactorer — improve structure, preserve behavior, never act without sign-off.

## Goal
Propose a clear restructuring plan, get explicit validation, then apply it with no behavior change.

## Deliverable
A validated plan, then the refactored files on disk + a passing verification + an updated `docs/specs/04-architect.md` if the structure changed.

---

## Hard rule

**No refactor without an explicitly validated plan.** This skill never edits code on first contact. It signals → proposes a plan → waits → only then applies. (Aligned with the global behavior rules.)

> If the project root has not been provided in this flow, first ask: `Project root? (folder path)`.

## Steps

1. **Load context**: `docs/specs/04-architect.md`, then `design-system.md`, `layout.md`, `@rules/mvvm.md` · `@rules/xaml.md` · `@rules/threading.md` · `@rules/security.md` (not auto-imported). If the app predates the Fluent baseline (README reference — see `/wpf-load-project` step 5), refactor within the app's own conventions; the upgrade path is `/wpf-migrate-design`, on request.

2. **Diagnose** what is actually wrong: duplication, a view's code-behind doing business logic, a god-service, a ViewModel touching a `Window`, a hardcoded value bypassing a resource key, a service resolved with `new` instead of injected, a bound property mutated off the UI thread. Anchor each finding to `file:line`.

3. **Decide per finding — factorize OR leave:**
   - **Factorize** when the blocks express the **same intent** (same operation, same data shape), are non-trivial (> ~5 meaningful lines of real logic), and a natural home exists (a `Helpers/` pure static method, a shared base ViewModel, a shared DTO in `Models/`) **without** forcing a long parameter bag or a `mode`/`kind` flag to fork behavior.
   - **Leave** when the blocks are coincidentally similar but conceptually independent, when factoring would force an unrelated layer to take a dependency, or when the shape will diverge soon. When in doubt, leave it.

4. **Propose the plan** (in the user's language): the findings, the proposed change per finding (factorize/leave + where the helper lives), the files touched, and the explicit promise of **zero behavior change** and **zero security or threading regression**. Wait for validation.

5. **Apply** only after validation. Minimum diff. Respect the layers, the contract, `@rules/security.md`, and `@rules/threading.md`.

6. **Verify**: `@rules/verification.md §A` — behavior unchanged, build and format clean. If the structure changed (new shared file, moved code, renamed service), update `docs/specs/04-architect.md`, regenerate the README (`@rules/readme.md`), and keep the DI registrations consistent with the new shape.

7. **Changelog**: append a `### Changed` entry under `## [Unreleased]` in `docs/release/CHANGELOG.md` (`@rules/versioning.md`) — in English, one line describing the internal restructuring, no version bump (the bump happens at `/wpf-release`; a refactor infers PATCH). If the file is absent (legacy app), skip silently and suggest `/wpf-load-project`. Skip if the refactor is trivially invisible (e.g. renamed a local variable).

## Anti-patterns — what NOT to do
- **Do not** refactor without a validated plan, ever.
- **Do not** factorize two blocks into a helper with a `mode`/`kind` flag that forks inside — that is two methods sharing a body.
- **Do not** create a shared abstraction or a base class "for the future" before a second real caller exists.
- **Do not** change behavior under the cover of a refactor — if behavior must change, that is `/wpf-add-feature`, declared separately.
- **Do not** weaken security or threading discipline while "cleaning up" (broadening a service surface, dropping a validation, removing a `CancellationToken`, adding an `async void`).
- **Do not** move a value out of `Themes/Tokens.xaml` or `AppConfig` into a local constant — refactors keep the centralization.
- **Do not** move an `sf` call out of `Services/SfCliService.cs` into a ViewModel or a view, or change a command/flag while refactoring — centralization is the injection guard (@rules/sf-cli.md; consult `sf-cli-reference/` by section to keep every command intact).
- **Do not** touch pre-existing dead code unless the user asked to remove it.

## When the user asks something adjacent
- **"Just clean it up however you think is best"** → still propose the plan first; "best" is a judgment the user should confirm before files move.
- **"Refactor and add X"** → split: the refactor (behavior-preserving, validated) and the feature X (`/wpf-add-feature`) are separate steps with separate validation.
